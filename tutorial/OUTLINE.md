# stressbot 使用教程 — 编写大纲

本文件是使用教程（面向压测使用者）的章节规划，作为后续逐章编写的依据。教程落点为 `tutorial/`，与现有 `docs/*.md`（面向维护者的技术参考）分工如下：

- **教程**（本目录）：按"完成一件事"的顺序组织，讲路径、讲取舍，示例配置可加载、每章有验收标准。
- **参考**（`docs/*.md` 与根 README）：按模块组织，讲全量字段、内部实现与边界。教程只链接，不复制内容，避免两处漂移。
- **重要前提**：参考文档与源码注释**不保证最新、准确**，仅作线索；教程的一切事实性内容以当前源码结构为准绳，每批写作前先做源码核对（见「二、源码核对」）。

读者画像（按优先级）：

1. **压测使用者**：拿到一个游戏服务器，要配置出一场压测；部署完成后，主要通过**前端界面**完成资源管理、流程编排、任务执行与监控。
2. **运维/部署者**：要把工具部署成常驻服务，或搭 Admin + 多 Agent 的分布式压测环境。
3. 二次开发者：已有 `docs/` + AGENTS.md 覆盖，不在教程目标内。

### 已定决策

1. **不附带 mock 游戏服务器**（2026-10 确认）。教程不引入新的常驻组件，端到端流量类验收统一以"读者自己的目标服务器"为前提。相应调整：
   - 贯穿案例 ArenaQuest 定位为**示例协议与配置讲解素材**：所有 flow / codec / proto 示例围绕它写，保证内容具体；但"可运行"标准降为**配置加载与前端校验通过**，涉及真实流量的验收标注【需目标服务器】。
   - 第 1 章快速开始的目标调整为"把工具跑起来并认识输出"；完整端到端压测在读者接入自己协议（第 4~5 章）后达成。
2. 教程语言：中文（与仓库约定一致）；界面术语遵守"Agent→节点、Admin→服务器"的 UI 用语约定，行文可用组件名（如 RuntimeBar）辅助定位，但以界面中文文案为主。
3. 是否需要英文版：暂缓，中文版稳定后再议。

教程全程使用虚构的迷你游戏 **「竞技场 (ArenaQuest)」** 作为示例协议（不复现其服务端）：账号登录 / 角色数据下发 / 心跳 / 商店浏览与购买 / 体力消耗 / 战斗匹配 / 战斗结果推送 / 公会广播，8~10 个消息覆盖请求-响应、推送、心跳、随机化、条件分支、错误码全部教学点。

- **示例落点**：`tutorial/examples/ch{NN}/`，每章一个目录，含该章完成后的完整 flow.json / codec 配置与增量说明。
- **可运行口径**：所有示例配置必须能通过 stressbot 加载期校验与前端编辑器校验报告；端到端流量验收标注【需目标服务器】。

## 二、源码核对：以源码为准绳（每批写作的前置工序）

现有 `docs/*.md`、根 README 乃至源码注释，在教程写作中一律定位为**线索与参考，不作为事实依据**——项目演进快，文档与注释可能滞后于代码。教程中每个事实性陈述（字段名、默认值、行为语义、界面文案）必须以**当前源码结构**为唯一依据产出。因此每批章节动笔前，先完成该批范围的源码核对，确认无误后再写：

### 核对方法

1. **数据模型对源码**：教程涉及的每个 JSON 字段与结构，对照 Go 结构体定义与 JSON tag（`flow/`、`binding/`、`engine/`、`network/`、`protocol/` 等），不对照文档表格。
2. **默认值与语义对实现**：默认值（如引擎默认节点间隔）、状态流转、错误语义，读实现代码与**测试用例**确认——测试往往是最准的行为文档。
3. **界面文案对组件源码**：第 15~20 章的每个按钮、弹窗、tooltip 文案，直接从 `cmd/web/src/components` 源码提取，不以文档描述或印象为准。
4. **示例配置跑校验**：核对产出的示例配置逐一通过 stressbot 加载期校验与前端编辑器校验，让校验器当第一读者。
5. **运行时行为实跑**：涉及运行语义的，按 AGENTS.md 验证流程实际运行 2~5 分钟观察，不凭文档断言。

### 差异处置

- 核对发现参考文档/注释与源码不符：**先修参考文档，再写教程章节**（同一批次内完成），不把已知偏差抄进教程——与仓库"过时内容物理删除"的约定一致。
- 源码行为与 AGENTS.md 约定不符：属代码问题，单独提出与维护者确认，教程不绕写、不臆测。

## 三、章节大纲

共 21 章分六部分。每章标注：目标 / 小节 / 示例产物 / 验收标准 / 引用参考 / 篇幅（S≤1 页，M 2~3 页，L 4 页以上）。

### 第 0 章 教程说明（S）

- 读者与适用版本；如何使用本教程（按序读 / 查目录跳读）。
- 全书目录与六部分导航；**建议阅读路径**：使用者 1→9、部署者跳 13→14、界面操作 15→21。
- 环境准备：Go 版本、目标服务器前置说明（无目标服务器时各章能走到哪一步）。
- **术语表**：机器人、节点（流程节点 vs 部署节点两种含义在首次出现时消歧）、监听、绑定、心跳、管理面/控制面、资源下发——全书用词与之一致。

### 第一部分：入门（第 1~4 章）

#### 第 1 章 快速开始：把工具跑起来（M）

- **目标**：30 分钟内完成编译、配置、启动，并认识监控输出与日志。
- **小节**：编译与目录结构 → `stressbot.toml` 最小可用配置逐项讲（log/monitor/standalone.bot）→ 启动命令与 `-flow` 切换场景 → 看什么：控制台监控输出、`log/*.log` → 无目标服务器时的可观察能到哪一步（连接失败也会产生监控样本与错误聚合，本身就是机制的演示）。
- **示例**：`ch01/` 最小 toml；引用仓库自带 `conf/flow/*.json` 场景样例导览（rank/guild/brawl 等各是什么类型的压测形态）。
- **验收**：进程启动、资源加载无 error；监控周期性输出；【需目标服务器】时机器人产生 Success 样本。
- **引用**：README「快速开始」、docs/configuration.md。

#### 第 2 章 架构总览：两种形态、三个二进制（M）

- **目标**：建立全局图景——工具由什么组成、我该用哪种形态、要准备什么。之后所有章节都能在这张地图上定位。
- **小节**：
  - 两种形态如何选：**单机**（一台施压机、快速验证、零外部依赖）vs **分布式**（多节点、大规模、集中管理与聚合监控；日常使用主路径是浏览器管理面）。
  - 三个二进制的职责边界：`stressbot`（单机全干一个进程）/ `admin`（浏览器管理面 + gRPC 控制面 + 任务调度与指标聚合）/ `agent`（执行节点，无本地控制面）。
  - 单机模式内部流水线（使用者视角）：TOML → 声明式 codec → proto 加载 → 流程配置 → 网络引擎 → 机器人批量/渐进启动。
  - 分布式组件关系图：浏览器 ↔ Admin（HTTP `/sbot/`）、Admin ↔ Agent（gRPC 长连接）、MySQL（任务/历史归档）、Redis（跨节点共享态）。
  - 依赖清单决策：什么时候完全不需要 MySQL/Redis（单机），什么时候需要哪个（分布式）。
- **示例**：`ch02/` 附两张架构示意图（单机流水线、分布式拓扑）源文件。
- **验收**：读者能回答"我的场景（如 5 万连接、3 台施压机）该选哪种形态、要准备几台机器和哪些依赖"。
- **引用**：docs/architecture.md、docs/distributed-architecture.md、README「架构概览」。

#### 第 3 章 核心概念：一个机器人的一生（M）

- **目标**：建立使用者需要的核心心智模型，之后所有章节不再解释这五个词。
- **小节**：机器人 = 一个客户端实例（Robot），Manager 批量创建 → 五个关键词：**流程 flow / 动作 action / 连接 service+channel / 状态 state / 监听 listen** → 单次动作数据流的使用者视角版（发请求→等响应→存字段）→ conf 四件套各司其职（flow / proto / scripts / adapter），以及分布式形态下它们经前端"资源管理"下发到节点的对应关系（预告第 16 章）。
- **验收**：读者能口头回答"一次 tcpRequest 从发到存经历了哪几步、中间哪一步可能超时"。
- **引用**：docs/architecture.md、README「架构概览」。

#### 第 4 章 让工具认识你的协议：proto 与 codec（L）

- **目标**：把读者的协议接进来，这是使用本工具的第一道门槛，也是最容易放弃的一章，要写得最细。
- **小节**：放 `.proto` 到 conf/proto（动态加载机制使用者视角：加载期报错的含义与排查）→ `*_codec.json` 命名规则 `<proto>_<service>` 与"每连接一份" → 头部字段声明与解析 → 加密配置（含 UDP 偏移部分加密的实际场景）→ `errors.json` 码段契约（<100 框架段 / ≥100 业务段，撞码报错）。
- **示例**：`ch04/tutorial.proto` + `tutorial_codec.json` + `errors.json`；一个手动 `tcpSend` 验证编码正确【需目标服务器】。
- **验收**：日志显示 codec 加载成功（以 ArenaQuest 示例即达成）；【需目标服务器】时对端收到格式正确的包。
- **引用**：docs/adapter-layer.md、docs/proto-schema.md、docs/error-code-system.md。

### 第二部分：流程编写（第 5~9 章）

#### 第 5 章 第一个流程：连接、登录、拿到数据（L）

- **目标**：写出最小完整流程，理解 nodes/actions 双表结构。
- **小节**：`nodes` + `actions` + `next` 跳转模型 → `tcpConnect`/`tcpClose` → `tcpRequest` 与 mainService → binding 三件套入门（fixed / state / randomInt）→ `store`：把响应字段存进 state（含嵌套 field 路径与 setter）→ 在日志/调试端点确认 state 内容。
- **示例**：`ch05/flow.json`：连接 → 登录 → 拉角色数据 → 打印 playerId（ArenaQuest 示例，加载校验通过；端到端【需目标服务器】）。
- **验收**：配置加载无 error；【需目标服务器】时机器人登录成功、state 中可见 playerId。
- **引用**：docs/flow-node-system.md、README「flow.json 结构」「bindings」「store」。

#### 第 6 章 流程控制：循环与分支（L）

- **目标**：能表达真实玩家行为的不确定性。
- **小节**：`sequence` → `loop`（无限 / 前置条件 / 后置条件 / break / continue）→ `boolean` / `switch`（首匹配、无 fall-through）/ `weighted` 加权随机 / `wait` → 条件表达式（`state:` / `lua:` 前缀，加载期强制；`&&`/`||`/`!`/括号复合）→ 节点执行间隔：任务级 `defaultDelayMs` 与节点级 `delayMs`（-1 禁用 / 0 用全局；UI 下发路径预告第 18 章）。
- **示例**：`ch06/flow.json`："循环刷体力副本直到体力不足" + weighted 随机挂机行为。
- **验收**：加载与前端校验通过；【需目标服务器】时监控中动作配比符合 weighted 权重。
- **引用**：README「节点类型」「条件表达式」，AGENTS.md 间隔约定。

#### 第 7 章 数据构造：随机化与过滤（M）

- **目标**：让一万个机器人各不相同。
- **小节**：随机类 binding 全览（randomPick(N) / randomPickMap / randomExclude / randomString charset / stateRandom(N) / randomMapKey/Value / randomFloat/Bool）→ 通用属性（optional / required / wrap / storeAs / path）→ `filters` 12 运算符与 mode（any/all/none）→ `map` binding 构造 proto map 字段 → `listSize`。
- **示例**：随机角色名、从商店列表按价格区间过滤后随机购买。
- **验收**：配置校验通过；【需目标服务器】时多机器人账号名不重复、过滤器命中的商品才被购买。
- **引用**：README「bindings」「filters」。

#### 第 8 章 推送与监听（M）

- **目标**：处理服务端主动推送，这是游戏压测区别于 HTTP 压测的关键能力。
- **小节**：`listens` 定义与 `listenRefs` 预注册 → `tcpListen`/`udpListen` 等待语义（队列边沿通知 + 超时）→ "推送先到、监听后启动"为什么不丢消息（预缓存）→ 监听指标：ListenReady / ListenTimeoutCount / ListenWait 直方图怎么读 → 回调与队列两种消费形态。
- **示例**：等待战斗匹配结果推送，超时走重试分支。
- **验收**：配置校验通过；【需目标服务器】时正常路径收到推送并 store、断推送路径监控 ListenTimeout +1。
- **引用**：README「listens」、docs/monitoring-system.md（监听指标节）。

#### 第 9 章 失败怎么办：onError 错误链路（M）

- **目标**：压测中错误是常态，流程要对错误有显式设计。
- **小节**：错误如何被记录（code 单维聚合、code<100 推导框架/业务标签、最近 3 条详情）→ `ignoreCodes`（warn 并继续，但监控保留失败样本）→ `handler` 普通节点调用边 → `retry.maxRetries` → `strategy`：resume / skip（由 sequence/loop/boolean/weighted 捕获）/ abort → 取消与超时的区分（ErrActionCanceled 归类 Canceled，停止机器人不算故障）。
- **示例**：购买返回业务错误码时降级重试；网络断开走重连分支。
- **验收**：配置校验通过；【需目标服务器】注入错误后流程按 strategy 预期恢复。
- **引用**：README「onError」、docs/error-code-system.md、docs/distributed-error-handling.md。

### 第三部分：进阶能力（第 10~12 章）

#### 第 10 章 心跳与连接保持（S~M）

- **目标**：长连接挂机不掉线。
- **小节**：声明式 per-connection 心跳配置 → 静态心跳 vs 动态心跳（body 变化，如计数器字段）→ 心跳与主流程的并发关系（connectionPump 独立推进，使用者视角：Lua 阻塞不影响心跳）。
- **示例**：ArenaQuest 动态心跳（带递增 seq）。
- **验收**：配置校验通过；【需目标服务器】长时间挂机无 CONN 类错误。
- **引用**：README「心跳」。

#### 第 11 章 Lua：声明式表达不了的行为（L）

- **目标**：知道边界——什么时候不该用 Lua；会用最常用的 20% API。
- **小节**：决策树（能 binding/条件表达就不用 Lua；跨动作复杂计算、动态协议行为才用）→ 脚本契约：`execute(r)` 返回 nil / err table `{code, detail}`（`robot.error` 构造）→ 常用模块速览（network / robot / proto / utils，只讲高频函数）→ **`robot.get` vs `robot.get_view` 一句话口诀**（整份加工用 get，大消息只读挑着看用 get_view）与 `network.tcp_listen` 惰性视图 → 范例逐行剖析 `conf/scripts/system_shop_buy.lua` → 阻塞语义：await/sleep 只暂停本机器人主流程。
- **示例**：用脚本实现"按背包剩余格子数决定购买数量"。
- **验收**：脚本可被加载执行；【需目标服务器】注入 errcode 后监控可见对应业务码。
- **引用**：docs/lua-runtime.md、AGENTS.md「get 与 get_view 使用边界」。

#### 第 12 章 加压策略与运行参数（M）

- **目标**：从"能跑"到"压得像真实负载"。
- **小节**：机器人数量与并发度 → `defaultDelayMs`（节点间隔的任务级配置，分布式形态在任务启动表单填写，预告第 18 章）→ `rampUp.stages` 渐进加压（阶段目标 / 并发 / holdSec，0 表未填回退 30s）→ `stateExtra` 初始状态与保留键保护（id/index/account 不可覆盖）→ 可选 Redis 跨节点共享态。
- **示例**：三阶段加压（爬坡 → 保持 → 冲刺）配置。
- **验收**：【需目标服务器】监控趋势图中机器人在线曲线呈阶梯状。
- **引用**：docs/ramp-up.md、docs/state-store.md。

### 第四部分：部署（第 13~14 章）

#### 第 13 章 部署实操：从源码到常驻服务（M）

- **目标**：在一台干净机器上把工具部署成可长期运行的服务。本章讲**单进程的编译、安装与守护**；多机组网是下一章。
- **小节**：
  - 编译与产物：三个二进制各自的构建命令、前端 `npm run build`、Makefile 一键构建、发布包结构（包根 `dist/` 前端产物、conf 摆放位置）。
  - 目录布局约定：二进制 / conf / log 的相对关系，`-config` 与资源路径 flag 的默认回退规则。
  - 前端托管两种形态：Admin 内置 staticDir 同源 vs nginx 独立部署（当前实际可用形态）。
  - 进程守护：Linux supervisor、Windows 常驻方式；开机自启。
  - 端口清单与健康检查：pprof/监控/管理面端口分别是什么、怎么探活。
  - 日志落盘与轮转；升级与回滚注意（配置兼容、历史归档保留）。
  - 可选观测栈导读：docker-compose 演示栈、`conf/deploy/` 下 nginx / grafana / loki / vector 样例各自的角色。
- **示例**：`ch13/` supervisor 配置样例 + 端口清单速查表。

## 四、写作规范（每章必须遵守）

1. **事实以源码为准**：字段、默认值、行为语义、界面文案一律源码核对后落笔（见「二、源码核对」）；参考文档与源码冲突时以源码为准，并回修参考文档。
2. **示例可校验**：每章 `examples/ch{NN}/` 含完整配置产物；代码块与示例文件内容一致，不接受伪代码；所有示例必须通过 stressbot 加载期校验与前端编辑器校验；端到端流量验收统一标注【需目标服务器】。
2. **验收标准**：每章末尾"你应该看到什么"，写清监控/日志/前端的具体可观察现象。
3. **教程不抄参考**：字段全量、内部实现一律链接 `docs/*.md` 或 README 对应节；教程只讲路径与取舍。
4. **中文行文**；错误信息引用仓库真实文案。
5. **与仓库约定同步**：UI 截图与描述以界面实际中文文案为准，不得暴露技术术语（Agent→节点、Admin→服务器）；教程过时内容物理删除，不留"旧版做法"注释。
6. **术语表统一**：以第 0 章术语表为准；"节点"在流程语境与部署语境两种含义必须消歧。
7. **前端章节的界面覆盖义务**（第 15~20 章）：每个面板、工具栏按钮、弹窗至少被一处正文覆盖并配截图；后续前端新增控件时，相应章节同步更新（进前端 PR 检查清单）。
