# 配置备份恢复加固设计

## 背景与目标

当前配置备份恢复已经覆盖已保存流程、当前编辑稿、Proto、Lua、协议配置、错误码、动作模板、监听模板和笔记文件，并具备合并导入、完整恢复、重复项处理、修订号校验及失败回滚。

本次加固解决五类问题：模板库存在绕过统一恢复协调器的独立导入路径；模板普通保存和备份解析的校验标准不一致；导出文件可能超过导入上限；连续模板变更可能让旧刷新结果覆盖新结果；“完整配置”的范围没有明确排除服务器环境数据。

目标是让所有用户配置导入统一走同一套可预检、可回滚的恢复路径，并确保系统能够重新导入自己生成的每一份备份。

## 交互与范围

文件菜单只保留“备份配置”和“恢复配置”作为跨模块配置迁移入口。删除“导入模板库”和“导出模板库”两个独立菜单及其专用 JSON 格式。用户若只需要迁移动作和监听模板，可在备份或恢复窗口中仅选择这两个分区。

共享模板库未启用时，动作模板和监听模板分区保持禁用，交互与历史按钮一致：说明需要检查服务器配置，不提供能力探测重试按钮。其他本地分区仍可正常备份和恢复。

备份窗口明确说明备份仅包含用户选择的可编辑配置，不包含服务器连接参数、数据库凭据、运行历史和界面偏好。`conf/config.json` 与 `conf/admin-config.json` 不进入备份，避免把环境相关配置和敏感信息带到其他服务器。

## 数据流与职责

### 统一导出

`ConfigBackupModal` 负责选择分区和展示估算大小，`createBackupBundle` 通过 `ConfigSectionRegistry` 读取并校验选中分区，`downloadBackupBundle` 负责最终序列化和下载。

最终序列化完成后必须检查 Blob 字节数。文件大于 `MAX_BACKUP_BYTES` 时中止下载并显示可操作的错误信息，要求减少所选内容；导入端继续使用同一常量检查文件大小。这样不会生成系统自身拒绝恢复的备份。

### 统一恢复

模板恢复继续使用现有 `ConfigRestoreModal`、`preflightRestore` 和 `executeRestorePlan`：

1. 解析带 `kind`、`schemaVersion`、manifest 和分区数据的统一备份文件。
2. 按模板名称精确判断重复项。
3. 支持全部覆盖、逐项处理、全部忽略和保留副本。
4. 对动作、监听和流程模板分别校验修订号。
5. 写入前保存恢复日志，失败时按逆序恢复已经开始写入的分区。

不再保留 `TemplateBundle`、`exportAllTemplates` 或 `importTemplates`，避免出现第二套格式、冲突规则和错误恢复语义。

### 模板保存校验

Admin 后端是模板数据的最终写入边界。普通创建、更新和快照替换必须复用同一套校验函数，至少与前端备份解析保持以下一致性：

- Action 的 pattern 必须合法并与 `data.pattern` 一致。
- 需要连接的 Action 必须提供 service；需要 route、address、c2sProto 或 s2cProto 的 pattern 必须提供对应字段。
- Lua Action 必须提供非空脚本，clearState 必须提供至少一个 key，HTTP Action 必须提供 URL，并限制支持的方法和内容类型。
- timeout 和 pollMs 必须是整数。
- Listen 的 kind 必须与内容形态一致；Lua Listen 的脚本不能为空。
- defaultRef 必须是对象，server 非空，route 非 null，queueSize 大于零。

后端校验失败返回现有 `INVALID_ARGUMENT`，且在数据库写入或快照删除前完成。前端分区校验补齐名称、描述、ID、时间和 defaultRef 的同等边界检查，使无效备份在预检阶段直接失败，而不是进入执行和回滚阶段。

### 模板列表刷新

`NodePalette` 为每次刷新分配递增序号。只有最新请求可以更新动作列表、监听列表和 loading 状态；较早请求即使更晚返回也必须被丢弃。

恢复仍可由动作、监听两个快照分别发送变更事件，但最终界面状态由最新刷新结果决定。该机制同时覆盖窗口聚焦、手动刷新和普通模板增删改触发的并发请求。

## 错误处理

- 备份过大：不创建下载链接，备份窗口显示“备份文件超过 100 MiB，请减少选择内容”。
- 模板能力不可用：模板分区和相关保存入口禁用，不发起模板读写请求。
- 模板数据无效：在普通保存或备份解析阶段返回具体字段错误，不执行数据库写入。
- 恢复期间失败：沿用恢复协调器的逆序回滚和持久恢复日志；本次不改变其事务语义。
- 模板刷新失败：保留最近一次成功列表并提示；过期请求的成功或失败均不覆盖最新请求状态。

## 测试设计

### 前端

- 工具栏测试确认不再渲染独立模板导入、导出菜单和隐藏文件输入。
- 备份 codec 测试确认恰好 100 MiB 可下载，超过上限时拒绝创建下载链接。
- 备份窗口测试确认显示用户配置范围说明，并能展示过大错误。
- section registry 测试覆盖无效 Action 必填字段、空 Lua Listen 脚本、无效 defaultRef、超长名称和非法时间。
- NodePalette 测试构造两个交错完成的刷新请求，确认旧响应不能覆盖新列表。
- 现有合并、完整恢复、冲突选择、修订号变化和逆序回滚测试继续通过。

### 后端

- Action 表驱动测试覆盖每类 pattern 的必填字段、HTTP 枚举值和整数约束。
- Listen 测试覆盖空 Lua 脚本和 defaultRef 边界。
- 快照测试确认无效数据在事务开始前被拒绝。
- 增加普通创建校验通过的数据能够进入快照并通过前端等价备份契约的代表性闭环用例。

### 完整验证

依次执行：

1. `go test ./admin -count=1`
2. `go build ./...`
3. `cd cmd/web && npx.cmd tsc -b`
4. `cd cmd/web && npm.cmd run test -- --maxWorkers=4`
5. `cd cmd/web && npm.cmd run build`
6. `git diff --check`

Go 命令使用项目内 `.tmp` 构建缓存，避免 Windows 用户级缓存权限影响验证结论。前端类型检查、测试和构建顺序执行，避免并行进程竞争 Vitest worker。

## 非目标

- 不把服务器运行配置、MySQL/Redis 凭据或历史记录加入备份。
- 不兼容独立模板 JSON 文件或旧版模板时间戳。
- 不引入跨多个 Admin 实例的数据库分布式锁；模板快照并发语义继续与流程模板保持一致。
- 不重构现有恢复协调器和恢复日志格式。
