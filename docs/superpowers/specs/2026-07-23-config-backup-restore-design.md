# 配置备份与恢复设计

## 目标

在现有“文件”下拉菜单中增加统一的“备份配置”和“恢复配置”入口。用户可以把多个配置模块导出为一个版本化 JSON 文件，并在同一服务器或其他 stressbot 环境中选择性恢复。

恢复同时支持两种语义：

- **完整恢复**：选中的模块最终与备份内容完全一致，会删除备份中不存在的现有内容。
- **合并导入**：不删除现有内容；发现重复项时支持全部覆盖、逐个处理或全部忽略。

该功能覆盖用户创建和维护的配置内容，不备份任务运行状态、历史报告、日志或纯界面偏好。

## 非目标

- 不替代现有流程 JSON、模板库、资源文件等单模块导入导出能力。
- 不备份正在运行的任务、任务历史、监控数据、运行日志或节点信息。
- 不备份主题、面板尺寸、日志筛选、任务启动表单等界面和运行偏好。
- 不把浏览器本地数据长期上传或保存到服务器。
- 首个版本不提供备份文件加密；界面明确提示文件可能包含业务配置和脚本，需要妥善保管。

## 已确认决策

1. 采用前后端协同架构：浏览器组装和下载单一备份文件，服务器只负责流程模板库的事务化快照读取与替换。
2. 导入和导出都允许选择模块；默认全选备份文件中可用的模块。
3. 恢复提供完整恢复与合并导入两种模式。
4. 合并导入的重复项处理参考文件复制：全部覆盖、逐个处理、全部忽略。
5. 逐个处理支持覆盖、保留两份、忽略，并可把当前选择应用到剩余同类冲突。
6. 入口放在当前“文件”下拉菜单中，使用“备份配置”和“恢复配置”的用户语义。
7. 流程模板恢复时保留原 ID 和时间，避免破坏历史记录中的来源流程引用。

## 数据范围

备份格式定义九个独立分区。界面可以把相关分区分组展示，但导入导出选择精确到分区。

| 分区键 | 用户界面分组 | 数据来源 | 主要内容 |
| --- | --- | --- | --- |
| `flows` | 已保存流程 | 服务器 MySQL | 流程、布局、ID、名称、创建和更新时间 |
| `draft` | 当前编辑稿 | Zustand + localStorage | 当前流程、画布布局、保存时间 |
| `protoFiles` | 资源 / Proto | IndexedDB | Proto 文件及同步元数据 |
| `luaFiles` | 资源 / Lua | IndexedDB | Lua 脚本及同步元数据 |
| `codecFiles` | 资源 / 协议配置 | IndexedDB | 全部 `*_codec.json` 及同步元数据 |
| `errorMap` | 资源 / 错误码 | IndexedDB | 单份 `errors.json` 及同步元数据 |
| `actionTemplates` | 模板库 / action | IndexedDB | action 模板及 ID、描述和创建时间 |
| `listenTemplates` | 模板库 / listen | IndexedDB | listen 模板、默认注册信息及元数据 |
| `notepadFiles` | 记事本 | IndexedDB | 文件 ID、名称、语言、内容及时间 |

未选择的分区不写入 `data`，不能用空数组代替。这样导入端可以区分“未备份该分区”和“备份时该分区为空”。

## 备份文件契约

文件名使用 `stressbot-config-backup-YYYYMMDD-HHmmss.json`，编码固定为 UTF-8。顶层结构：

```json
{
  "kind": "stressbot-config-backup",
  "schemaVersion": 1,
  "exportedAt": "2026-07-23T15:30:00+08:00",
  "manifest": {
    "includedSections": [
      "flows",
      "draft",
      "protoFiles",
      "luaFiles",
      "codecFiles",
      "errorMap",
      "actionTemplates",
      "listenTemplates",
      "notepadFiles"
    ],
    "counts": {
      "flows": 8,
      "draft": 1,
      "protoFiles": 12,
      "luaFiles": 20,
      "codecFiles": 4,
      "errorMap": 1,
      "actionTemplates": 6,
      "listenTemplates": 3,
      "notepadFiles": 9
    }
  },
  "data": {
    "flows": [],
    "draft": {},
    "protoFiles": [],
    "luaFiles": [],
    "codecFiles": [],
    "errorMap": {},
    "actionTemplates": [],
    "listenTemplates": [],
    "notepadFiles": []
  }
}
```

约束：

- `kind` 必须精确匹配，避免把流程 JSON 或模板库 JSON 误当成完整备份。
- `schemaVersion` 首版为 `1`。高于当前支持版本时拒绝导入；旧版本通过显式、纯函数迁移链升级后再校验。
- `manifest.includedSections` 与 `data` 的键必须一致，`counts` 必须与校验后的实际项目数一致。
- 每个资源项完整保存 `name`、`content`、`size`、`uploadedAt`、`baseHash`，恢复后继续保持正确的基线三方比较语义。
- 选中的空数组分区写为 `[]`；选中但没有内容的单例分区 `draft` 和 `errorMap` 写为 `null`，对应 count 为 `0`。未选择分区仍然完全省略。
- 不导出原始 IndexedDB 或 localStorage 键，不把内部存储布局当成长期兼容契约。
- 浏览器拒绝读取超过 100 MiB 的备份文件，并在选择文件后立即提示，不进入 JSON 解析。

## 菜单和交互

### 文件菜单

保留现有菜单项，在现有流程和模板导入导出之后增加分隔线：

1. 备份配置...
2. 恢复配置...

使用独立菜单项而不是一个二级入口，减少常用灾备操作的点击层级。

### 备份配置

备份弹窗展示分组复选框、每个分区的项目数和估算大小：

- 已保存流程
- 当前编辑稿
- 资源：Proto、Lua、协议配置、错误码
- 模板库：action、listen
- 记事本文件

默认选择全部可用分区，提供全选和清空。没有项目的分区仍可选择，导出后明确表示该分区为空，便于完整恢复时清空目标模块。至少选择一个分区后才能下载。

流程库未启用时，“已保存流程”禁用并显示“服务器未启用流程库”，其余本地分区仍可正常备份。

备份任何已选分区读取失败时不生成文件，错误提示指出失败分区。不能静默下载缺少已选内容的部分备份。

### 恢复配置

恢复弹窗分为预检和执行两个阶段：

1. 选择备份文件。
2. 展示格式版本、导出时间、包含分区和校验结果。
3. 选择本次恢复的分区；只能选择文件中包含的分区。
4. 选择“合并导入”或“完整恢复”。
5. 合并导入时选择重复项默认策略：全部覆盖、逐个处理、全部忽略。
6. 展示预计新增、覆盖、删除、忽略和保留两份的数量。
7. 二次确认后执行恢复。

完整恢复的确认文案必须明确“会删除选中模块中备份不存在的内容”。恢复只允许在编辑模式执行；运行、查看任务和最终报告模式可以读取并预检备份，但“开始恢复”禁用并提示先返回编辑。

备份始终可用。编辑模式下的 `draft` 从当前内存流程和布局捕获，确保未等到 debounce 的修改也被保存；非编辑模式下从最后保存的编辑稿读取，不能把只读运行画布误当成用户草稿。

### 冲突清单

“逐个处理”只在确实存在冲突时打开清单。清单按分区分组，每项展示来源名称、目标名称、更新时间和内容摘要，提供：

- 覆盖
- 保留两份
- 忽略

每个选择都支持“应用到剩余同类冲突”。所有冲突处理完成后才生成最终恢复计划和执行写入，不能边询问边修改数据。

单例分区 `draft` 和 `errorMap` 不支持保留两份，只提供覆盖或忽略。

## 恢复语义

### 完整恢复

完整恢复只作用于本次选中的分区：

- 目标分区中备份不存在的内容删除。
- 备份内容完整写入，并保留可保留的 ID 和时间元数据。
- 未选中的分区完全不读取、不清空、不刷新。
- 备份中显式包含但为空的分区会清空目标分区。

### 合并导入

合并导入不删除备份中不存在的目标内容：

- 非重复项追加。
- 重复项按全部覆盖、全部忽略或逐个处理结果执行。
- “保留两份”生成新的内部 ID 和唯一名称，原项与导入项同时存在。
- 恢复计划在写入前固定，执行阶段不再弹出决策窗口。

### 重复判断

| 分区 | 重复条件 |
| --- | --- |
| `flows` | ID 相同，或流程名称精确相同 |
| `draft` | 目标存在编辑稿即冲突 |
| `protoFiles` | Proto 分区内文件名精确相同 |
| `luaFiles` | Lua 分区内文件名精确相同 |
| `codecFiles` | 协议配置分区内文件名精确相同 |
| `errorMap` | 目标存在 `errors.json` 即冲突 |
| `actionTemplates` | ID 相同，或 action 模板名称精确相同 |
| `listenTemplates` | ID 相同，或 listen 模板名称精确相同 |
| `notepadFiles` | ID 相同，或记事本文件名精确相同 |

名称和文件名比较沿用当前各模块的精确匹配语义，不擅自改成大小写不敏感。ID 和名称分别命中不同目标时视为一个需要逐个处理的歧义冲突，不能自动覆盖两个目标。

### 保留两份命名

保留两份时使用当前模块名称生成规则，在扩展名前追加“（副本）”，继续冲突时追加递增序号：

```text
login.lua
login（副本）.lua
login（副本 2）.lua
```

流程、模板和记事本使用相同后缀。若冲突来自相同 ID，导入副本生成该模块格式的新 ID；流程使用 `nanoid(32)` 生成适配 `VARCHAR(32)` 的 ID，模板和记事本沿用各自现有 ID 生成规则。

## 前端架构

新增独立的配置传输模块，避免把跨模块逻辑堆入 `Toolbar.tsx`：

```text
components/modules/configTransfer/
  ConfigBackupModal.tsx
  ConfigRestoreModal.tsx
  ConflictResolutionView.tsx
  RestoreResult.tsx

services/configTransfer/
  types.ts
  backupCodec.ts
  sectionRegistry.ts
  restorePlanner.ts
  restoreCoordinator.ts
  recoveryJournal.ts
```

### 分区适配器

`sectionRegistry` 为九个分区注册适配器。统一接口负责：

- 读取当前内容
- 校验备份内容
- 计算重复项和差异
- 根据恢复计划写入最终内容
- 刷新该模块的运行时状态

适配器只暴露分区级能力，不让 UI 直接操作 IndexedDB、localStorage 或流程 API。纯解析、校验和计划逻辑放在 `backupCodec` 与 `restorePlanner` 中，便于在无浏览器数据库的 Vitest 环境中测试。

### 现有存储模块扩展

- `resourcesStore.ts` 增加按 `ResourceFile` 原样读取和完整替换的方法，保留 `baseHash` 与时间，不复用会重新生成元数据的普通上传函数。
- `templateStore.ts` 增加完整替换和按最终列表写入方法；批量操作只发送一次模板变更通知。
- `notepadStore.ts` 增加导出完整文件、完整替换和刷新方法；导出前先冲刷所有 debounce 保存。
- `persistDraft.ts` 增加读取当前编辑稿快照和应用编辑稿快照的方法。
- `flowsApi.ts` 增加流程快照读取和事务替换 API。

### 状态刷新

恢复成功后只刷新选中的模块：

- 资源发送一次统一变更通知并刷新 Proto/codec 派生缓存。
- 模板库发送一次变更通知。
- 记事本重新加载索引；当前文件不存在时清空选择。
- 选中 `draft` 时把恢复后的流程和布局加载到编辑器，并重新计算校验报告。
- 选中 `flows` 时刷新流程管理列表。

## 后端架构

流程模板库新增两个端点：

```text
GET /sbot/flows/snapshot
PUT /sbot/flows/snapshot
```

读取响应：

```json
{
  "revision": "sha256:...",
  "items": []
}
```

替换请求：

```json
{
  "expectedRevision": "sha256:...",
  "items": []
}
```

`items` 是前端根据完整恢复或合并规则计算出的最终权威列表。后端不重复实现 UI 冲突策略，只负责验证、并发保护和事务替换。

`FlowTemplateStore` 增加进程内读写锁，所有现有流程 CRUD 与快照 API 都通过同一锁访问，避免预检和替换期间被当前 Admin 进程的其他请求穿插修改。快照列表按 ID 稳定排序，并对 ID、名称、flow、layout、创建时间和更新时间的规范化表示计算 revision。

`PUT` 执行顺序：

1. 限制请求体大小为 50 MiB。
2. 在事务外完成全部名称、ID、flow JSON、layout JSON、重复 ID 和数量校验。
3. 获取写锁并开启 MySQL 事务。
4. 读取当前列表并计算 revision；与 `expectedRevision` 不一致时回滚并返回冲突。
5. 删除旧流程并批量插入最终列表，保留请求中的 ID、创建和更新时间。
6. 提交事务并返回新 revision 和统计。

该锁只承诺单 Admin 进程内的一致性，符合当前部署模型；不宣称支持多个 Admin 实例直接共享同一流程表并发写入。

`GET /sbot/capabilities` 增加 `flowLibrary` 布尔字段，前端据此禁用流程分区，而不是等用户点击后才报错。

## 导出数据流

1. 弹窗加载每个分区的项目数和可用状态。
2. 用户选择分区并点击下载。
3. 协调器并行读取互不依赖的本地分区；流程分区通过快照 API 读取。
4. 任一已选分区失败时终止，不生成部分文件。
5. 按 `schemaVersion: 1` 生成结构，重新计算 manifest 数量。
6. 使用 Blob 生成一个 JSON 下载并立即释放 object URL。

导出只读取数据，不修改本地同步基线或服务器流程 revision。

## 导入与恢复数据流

### 预检

1. 检查文件大小和 JSON 格式。
2. 校验 `kind`、版本、分区清单、数据结构、唯一键、文件名和模块专属约束。
3. 运行版本迁移后再次完整校验。
4. 读取用户选中分区的当前内容和流程 revision。
5. 计算新增、覆盖、删除、忽略、保留两份和歧义冲突。
6. 完成全部冲突决策，生成不可变恢复计划。
7. 执行前重新读取摘要；目标内容已变化时废弃计划并要求重新预检。

预检期间不修改任何配置。

### 恢复日志

写入前在独立 IndexedDB `stressbot-config-recovery` 中保存：

- 操作 ID、开始时间和当前阶段
- 选中分区
- 各分区写入前快照
- 服务器流程写入前快照与 revision
- 已完成分区和回滚状态

恢复日志写入失败或空间不足时中止，不开始覆盖。成功完成并刷新状态后删除恢复日志。

### 执行

1. 通过 `PUT /flows/snapshot` 事务替换最终流程列表；未选择流程分区时跳过。
2. 按资源、模板、记事本、编辑稿顺序应用本地分区最终列表。
3. 每完成一个分区立即更新恢复日志。
4. 全部分区成功后刷新运行时状态。
5. 删除恢复日志并展示结果统计。

### 失败补偿

任一步失败后停止后续写入，并逆序恢复已完成分区。服务器流程使用日志中的旧快照，以及本次流程替换成功后服务器返回的 `appliedRevision` 做补偿替换。

若流程库在替换成功后又被其他请求修改，补偿请求会因 revision 不匹配而拒绝，不能强行覆盖新修改。恢复日志保留该冲突并要求人工重新预检，其他可安全回滚的本地分区仍继续回滚。

浏览器启动时检测未完成恢复日志并自动继续回滚。服务器不可达或回滚仍失败时保留日志，在顶部显示不可忽略的“配置恢复未完成”状态，列出待回滚分区并提供重试。界面不能在日志未清除时报告恢复成功，也不能开始第二次恢复。

MySQL 与多个浏览器 IndexedDB 之间不存在真正的分布式事务；该设计提供持久日志和可重试补偿，不使用“全局原子事务”描述其保证。

## 校验与安全

- 解析后对每个字段做结构化校验，不能仅依赖 TypeScript 类型断言。
- 流程继续复用现有前端流程校验，服务器再次校验 flow JSON 和名称。
- Proto 和 Lua 只作为 UTF-8 文本保存，导入阶段不执行脚本。
- codec 文件复用 `validateCodecSchema`；`errors.json` 必须是合法对象并继续遵守框架错误码保留段规则。
- 文件名复用各资源模块现有扩展名和命名限制。
- 所有名称在 React 中按文本渲染，不使用 `dangerouslySetInnerHTML`。
- 恢复只写浏览器存储和流程模板表，不写服务器文件系统路径。
- 弹窗提示备份文件可能含业务协议、脚本和笔记内容，首版不提供密码或加密功能。

## 错误与能力降级

- 备份格式错误：展示第一个阻断错误和分区位置，不进入恢复选择。
- 更高格式版本：提示使用更新版本的 stressbot，不能尝试降级读取。
- 流程库未启用：流程分区禁用；其他分区可继续操作。
- 流程 revision 变化：返回 HTTP 409 和 `FLOW_SNAPSHOT_CONFLICT`，重新执行预检，不能覆盖刚产生的其他用户修改。
- 本地存储配额不足：在恢复日志写入阶段中止，现有配置保持不变。
- 单分区读取失败：备份中止；不能下载缺少该分区的文件。
- 单分区写入失败：进入补偿回滚并保留恢复日志，展示实际阶段。
- 回滚失败：保留恢复日志和显著状态入口，允许用户重试；不能用普通 toast 掩盖。

## 测试与验收

### 前端纯逻辑测试

- 任意分区组合只导出选中数据，manifest 与内容一致。
- 显式空分区与未包含分区严格区分。
- 非法 JSON、错误 kind、缺失字段、重复键、错误 counts 和高版本全部拒绝且不写数据。
- 九个分区分别覆盖新增、重复、删除和保留两份计划。
- 合并模式覆盖全部覆盖、全部忽略和逐个处理。
- ID 与名称分别命中不同目标时生成歧义冲突。
- 完整恢复只删除选中分区中的额外内容。
- 副本名称和新 ID 生成稳定且无二次冲突。

### 前端存储与协调测试

- 资源完整恢复保留 `baseHash`、`uploadedAt` 和内容。
- 模板批量恢复只发一次通知。
- 记事本导出先冲刷 debounce，恢复保留内容和时间。
- 当前编辑稿在编辑模式捕获内存状态，在非编辑模式不误用运行画布。
- 流程库禁用时本地分区仍可备份恢复。
- 模拟每个执行阶段失败，验证已完成分区逆序回滚。
- 模拟页面中断后重新加载，验证恢复日志继续回滚并阻止第二次恢复。

### 后端测试

- 快照导出包含所有流程并保留 ID、布局和时间。
- 快照 revision 对稳定排序后的相同内容保持一致。
- 替换请求中的任一非法流程导致整个事务不写入。
- 正常替换删除旧列表并写入最终列表。
- `expectedRevision` 不一致返回冲突且不写入。
- 流程库未启用时两个快照端点返回现有禁用错误语义。
- 请求体超过 50 MiB 时拒绝。

## 兼容与迁移

- 首版只写 `schemaVersion: 1`。
- 读取路径必须先按版本迁移到当前内部结构，再执行统一校验和计划。
- 未知顶层扩展字段可以忽略，但未知分区键必须拒绝，避免用户误以为某类内容已恢复。
- 现有模板库独立 JSON、流程 JSON 和资源文件不能直接在“恢复配置”入口导入；用户继续使用原有单模块入口。
- 本功能不修改现有 IndexedDB 名称，新增能力通过各存储模块的显式 API 访问现有数据。

## 设计取舍

前端直接逐条调用现有流程 CRUD 虽然改动较小，但无法在批量恢复中保证流程库一致，也难以保留原 ID 和时间，因此不采用。

把全部本地数据上传给服务器可以集中处理文件，但会让服务器理解浏览器私有存储格式，并把记事本等本地内容发送到服务端，因此不采用。

最终方案让浏览器拥有备份文件和冲突规划，让服务器只拥有流程模板事务。跨存储恢复通过持久日志与补偿回滚实现，诚实暴露其不是分布式原子事务，同时满足完整恢复、选择性恢复和可重试失败处理。
